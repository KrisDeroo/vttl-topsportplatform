# Phase 3 — UI Design Contract — Kalender

> Visual and interaction contract for the calendar surface — the central daily work surface of the VTTL Topsportplatform and the most complex UI component of the project (per ROADMAP). Generated by gsd-ui-researcher; consumed by gsd-planner, gsd-executor, gsd-ui-checker, gsd-ui-auditor. **Builds on Phase 1 chrome and Phase 2 visual language — does not redesign either.**
>
> **Localization rule (hard, inherited from Phase 2):** Every user-facing UI string is referenced as an i18n key. Literal copy appears only inside the `## Copywriting Contract` table (nl/en/fr columns) so the planner can populate `messages/{nl,en,fr}.json`. No literal strings inside components. **One Phase-3-specific exception:** FullCalendar's built-in view buttons (`week`, `day`, `month`, `year`), weekday names, month names, time format, and a11y strings are owned by the FullCalendar `@fullcalendar/core/locales/{nl,en-gb,fr}` packages — those catalogs replace our message keys for the calendar-internal chrome. App-level toolbar above the calendar (filter bar, "Nieuwe afspraak" CTA, page title) uses our own i18n keys per the standard rule.
>
> **No CONTEXT.md for Phase 3 — design decisions in this spec marked `[default]` are best-fit choices given upstream constraints. The user may override any `[default]` before checker approval; once checker stamps `status: approved` they are locked.**

**Phase 3 declared exceptions (all on 4-pt grid):**

- FullCalendar grid cell minimum height: `h-12` (48px) per hour-row on desktop, `h-16` (64px) per hour-row on mobile single-day view — both keep events visually parseable at typical zoom.

## Typography

Inherited from Phase 2. **Three sizes + one display, two weights — strict. No new typography roles introduced for Phase 3.**

| Role | Size | Weight | Line Height | Tailwind |
|------|------|--------|-------------|----------|
| Body | 14px | 400 (regular) | 1.5 (21px) | `text-sm leading-relaxed` |
| Label / Form | 14px | 500 (medium) | 1.4 | `text-sm font-medium` |
| Heading (Sheet title, Card title) | 18px | 600 (semibold) | 1.3 | `text-lg font-semibold` |
| Display (Page title) | 24px | 600 (semibold) | 1.25 | `text-2xl font-semibold` |

**Calendar-internal text (FullCalendar-managed):**

- Day header row (Mon/Di/Wo or Mon/Tue/Wed): renders at 14px / 500 weight via `--fc-button-text-color`, `--fc-page-bg-color` overrides — **same `text-sm font-medium` as our Label role.** Locked via FullCalendar CSS-variable override in `globals.css` Phase-3 section.
- Time-axis labels (08:00, 09:00, ...): 12px / 400 weight via `--fc-small-font-size: 0.75rem` override. **This is the ONE Phase-3 exception to the "no `text-xs` for user-facing text" rule.** Rationale: FullCalendar's time-axis is dense by design; 14px breaks the grid. The override is scoped to the FullCalendar root element only — never bleeds to other surfaces.
- Event chip title text: 14px / 500 weight (same as Label). Truncates with `text-overflow: ellipsis` on a single line at week view; wraps to 2 lines max on day view via custom `eventContent` callback (see `## Event Chip Contract`).
- Event chip secondary line (location, role): 12px / 400 weight via `text-xs text-muted-foreground` — second Phase-3 exception, same rationale + scope.

> **Forbidden elsewhere in Phase 3:** Free use of `text-xs` outside FullCalendar's root and the event-chip secondary line. Tooltip body text inside `EventDetailSheet` stays at 14px. **No third weight added** (no `font-bold`, no `font-light`).

## Color

shadcn neutral preset (already in `globals.css`) provides the chrome palette. Phase 3 inherits the chrome layer 1:1 from Phase 2 and **introduces a sixth semantic axis: event-type color tokens**. These are the only new color tokens Phase 3 adds.

### Chrome palette (60/30/10 — inherited, unchanged)

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--background` | Page background, FullCalendar grid background (override `--fc-page-bg-color: var(--background)`) |
| Secondary (30%) | `--muted` / `--card` | Sheet body background, filter-bar background, FullCalendar header row (override `--fc-neutral-bg-color: var(--muted)`), today-cell highlight (override `--fc-today-bg-color: var(--muted)`) |
| Accent (10%) | `--primary` | Reserved for the **two surfaces below ONLY** |
| Destructive | `--destructive` | Delete event confirmation, infected-scan warning if event attaches a file (Phase 5 carry-forward placeholder) |
| Border | `--border` | Card outline, Sheet outline, FullCalendar grid lines (override `--fc-border-color: var(--border)`) |
| Foreground (text) | `--foreground` | Body text, headings, event chip text on neutral chips |
| Muted foreground | `--muted-foreground` | Helper text, time-axis labels, empty-state copy |

**Accent (`--primary`) reserved in Phase 3 for (explicit list — short and audited):**

1. The "Nieuwe afspraak" primary CTA button in the calendar toolbar (`Button variant="default"`) — single surface.
2. The currently-selected view button in FullCalendar toolbar (override `--fc-button-active-bg-color: var(--primary)` + `--fc-button-active-text-color: var(--primary-foreground)`). Inactive view buttons use `--fc-button-bg-color: var(--secondary)`.

**Accent NOT used for:** event chips (each event type has its own token — see below), filter chips (use `--secondary` / `--muted` for toggle-off, `--secondary-foreground` text), today-cell tint (uses `--muted`), focus rings (use `--ring`), filter combobox selections (use `--secondary`), or the locale switcher (Phase 1 `outline` style).

### Event-type color tokens (NEW — Phase 3)

CAL-03 mandates: trainingen **blauw**, toernooien **oranje**, vergaderingen **groen**, stages **paars**, evaluatiegesprekken **geel**, medische afspraken **rood**.

Implementation approach: **left-border accent + low-saturation tinted background + dark text on chip**, NOT solid colored block with white text. Rationale:
1. WCAG AA contrast at 14px label weight is easier with dark text on tinted-light background than with white text on saturated background (especially geel — yellow chips with white text fail at any saturation).
2. Color-blind safety: the left-border + icon strategy means red/green deuteranopes still distinguish via the lucide icon glyph in the chip (see `## Event Chip Contract`).
3. Visual calm: six saturated blocks side-by-side becomes optically loud at week view density (~40–60 events visible at once for a TD). Tinted chips read as a system, not as decorations.
4. Token portability: dark mode keeps the same hues but inverts background-vs-foreground so contrast holds.

> **Why six new color tokens instead of using Tailwind blue-100 / orange-100 / etc.?** Three reasons: (1) Tailwind v4 in this repo is CSS-first with no `tailwind.config.*` — there is no place to declare "blue-100" semantics; (2) dark-mode parity requires both light and dark values per token, which Tailwind palette literals do not provide; (3) the tokens make the color contract auditable in one place (this file) and future tweaks (e.g. tweaking trainer-blue saturation after UAT) become a one-line change in `globals.css`.

> **Conflict with `--destructive`?** Medical-red token is distinguishable from `--destructive` red: `--cal-event-medical-border` is L=0.55 / C=0.20, `--destructive` (Phase 1) is L=0.577 / C=0.245. Close enough to read as "the red family", different enough that a destructive button never blends visually with a medical chip. **Rule:** medical chips do NOT use `--destructive` and the delete-event confirmation button does NOT use `--cal-event-medical-*`.

## Page Surfaces (Routes)

All routes live under `src/app/[locale]/(app)/` (D-39 from Phase 2). All pages are Server Components by default; the calendar itself is a Client Component (FullCalendar requires browser APIs — `'use client'` boundary lives at the `<CalendarView>` component, not the page).

| Route | Component layout | Visible to | Title key |
|-------|------------------|------------|-----------|
| `/calendar` | Page header (H1 + filter summary chips + "Nieuwe afspraak" CTA if role can create) → CalendarToolbar (view switcher, date navigator, filter trigger) → `<CalendarView>` (FullCalendar) → ConflictBanner (slot, hidden by default) | Authenticated user (all roles). Server-side `requireAuth` redirect to `/login` if anonymous. Empty events list does NOT redirect — calendar shell still renders. | `calendar.title` |
| `/calendar/event/[id]` | Same as `/calendar` (re-render the calendar) + auto-opens `<EventDetailSheet>` for the given event. If RBAC scope filters the event out → opens a "Niet gevonden" toast and removes `?event=` from URL. | Authenticated user; server reads event by id then RLS-filters per CallerContext. Out-of-scope → 404 sheet body identical to deleted-event sheet body (D-36 carry-forward: never reveal whether the event exists in someone else's scope). | `calendar.event.title` |

> **Why not a separate route per view?** FullCalendar's view switching is internal state. We persist the selected view in the URL as `?view=week\|day\|month\|year` (default `week`) so deep links survive refresh and back/forward navigation. Date navigation persists as `?date=YYYY-MM-DD` (default = today in user's timezone). Filter state persists as `?filter=…` (described in `## Filter Bar Contract`).

> **`/me/calendar` shortcut?** Out of scope for Phase 3. `/calendar` IS the speler's view when the speler's CallerContext filters server-side. No separate "my calendar" route — keeps the surface count low. Players land on `/calendar` and see only their own events because RLS + tRPC `calendar.list` does the filtering.

### Page-level layout grid

- Top app chrome: 56px tall (`h-14`), inherited from Phase 1.
- Content: **full-width** with `mx-auto` and `max-w-screen-2xl` (1536px) — wider than Phase 2's `max-w-5xl` so a TD watching 7 days × ~14 hours has comfortable horizontal space. On screens > 1536px, calendar centers with white space on either side.
- Side padding: `px-4` on mobile, `px-6` on `md:` and up. Phase 2's `px-6` desktop standard preserved.
- Vertical rhythm: `py-6` (24px) below chrome to put calendar high on the viewport (no `py-8` like Phase 2 forms — calendar wants vertical real estate).
- Toolbar → calendar gap: `mt-4` (16px).

### Empty state

Calendar is NEVER fully empty in v1 (player always has at least themselves — even before any events exist, the grid shows). When server returns zero events for the selected range, the FullCalendar grid still renders empty cells. Below the calendar, a **subtle informational strip** (not a Card, not centered, not blocking) renders:

- lucide `CalendarOff` icon (size 16, `text-muted-foreground`) + body line: `calendar.emptyHint`.
- Wired only when filters are NOT active and the visible range has 0 events. When filters ARE active and 0 events result, the strip swaps to `calendar.emptyFiltered` with a "Filters wissen" button.

> **No card-style empty state like Phase 2.** The calendar grid IS the empty state — drawing attention away from it with a centered Card would obscure the affordance to navigate days/weeks/months. The strip is supplementary, not the primary affordance.

## Event Chip Contract — `eventContent` Callback

FullCalendar's `eventContent` callback returns a JSX node embedded in the calendar's event element. Critical: the returned node is NOT a full React component — no hooks, no context consumption. All data must arrive via `event.extendedProps`.

### Visual shape (week + day view — `timeGrid`)

```
┌────────────────────────────────────────┐
│ ▌ 🏓 09:00–10:30                       │   ← left border 2px (type color), icon, time
│ ▌ Training Senioren A                  │   ← title (14px/500, truncate)
│ ▌ ⌖ Topsportschool — Trainer J. Peeters│   ← optional 2nd line (12px/400)
└────────────────────────────────────────┘
```

- Left border: 2px solid in `--cal-event-{type}-border`.
- Background: `--cal-event-{type}-bg`.
- Foreground (text + icon): `--cal-event-{type}-fg`.
- Padding: `px-2 py-1` (8px / 4px).
- Border-radius: `rounded` (4px — matches `--radius-sm`).
- Icon glyph (lucide) per event type:
  - Training: `Dumbbell`
  - Tournament: `Trophy`
  - Meeting: `Users`
  - Stage: `MapPin`
  - Eval conversation: `MessagesSquare`
  - Medical: `Stethoscope`
- Icon + start–end time render on a single line at the top. Title on line 2. Optional location/owner on line 3 (only on `timeGridDay` where vertical space allows; suppressed in `timeGridWeek`).

### Visual shape (month view — `dayGrid`)

Compressed mode: single line per event, icon + title only, time prefix in 12px monospace-ish (`tabular-nums`):

```
▌ 09:00 🏓 Training Senioren A
```

- No title wrap. `text-overflow: ellipsis` on overflow.
- Stacks up to 4 events per day; 5th+ collapses into "+N meer" overflow link (FullCalendar built-in `dayMaxEvents`).

### Visual shape (year view — `multiMonth`)

Year view shows month grids without per-event detail. Each day cell that has events gets a 4px-wide colored bar at the bottom whose color is the type of the **most-recent** event that day (FullCalendar's built-in "background event" rendering won't be used — we override `dayCellContent` to render a small `<div className="h-1 w-full rounded-sm" style={{ background: '...' }} />` whose color is computed from the day's events). When a day has events of multiple types, the bar splits into N stripes (max 3 visible, "..." indicator if more). Click on a day in year view → navigates to week view of that date.

### Status overlays

| Overlay | Trigger | Visual |
|---------|---------|--------|
| Past event | `event.end < now` | `opacity-60` applied to the chip |
| Currently happening | `event.start <= now <= event.end` | 2px solid outline ring inside the chip in `--primary/40` |
| Recurring | `event.extendedProps.hasRrule === true` | tiny `Repeat` icon (lucide, 10px) appended after icon on line 1 |
| Conflict (overlap detected client-side) | `event.extendedProps.conflicting === true` | tiny `AlertTriangle` icon (lucide, 10px) appended after time on line 1 — non-blocking visual hint; server is source of truth for conflicts |
| Cancelled (Phase 4 exception flag) | `event.extendedProps.status === 'cancelled'` | strikethrough on title + 50% opacity. Phase 3 supports the visual; the cancelled state is introduced in Phase 4. |

### Accessibility

- The chip itself is a focusable element (FullCalendar renders it as `<a>` by default; we add `aria-label` via the `eventDidMount` hook concatenating title + start time + type label).
- Color-state is also conveyed by the icon glyph (deuteranopia safety).
- Keyboard: Tab moves between events; Enter opens the `EventDetailSheet`.

## Filter Bar Contract

CAL-05 requires filters by: speler, trainer, sparring partner, academie, evenementtype.

### Desktop (≥ 768px) — inline bar

Renders directly under `CalendarToolbar` and above `CalendarView`. Single row with `flex flex-wrap gap-2`:

[Type:] [Training] [Toernooi] [Vergadering] [Stage] [Gesprek] [Medisch]    [Speler ▾]  [Trainer ▾]  [Sparring partner ▾]  [Academie ▾]   [✕ Wissen]

### Mobile (< 768px) — bottom sheet

- Filter row collapses to a single `Button` showing "Filters · N" (count of active filters across categories) with `SlidersHorizontal` icon.
- Click opens a `<Sheet side="bottom">` containing the same controls stacked vertically with `space-y-4`.
- "Toepassen" CTA at the bottom of the sheet (primary), "Wissen" secondary link below it.

### URL persistence

Active filters serialize to `?filter=` as a base64-encoded JSON object: `{ types: ['training','tournament'], players: ['uuid-a','uuid-b'], trainers: [...], sparring: [...], academies: [...] }`. Empty arrays omitted. Decoded server-side and passed into `trpc.calendar.list` so server-side filtering is the source of truth. **Filter values that the caller no longer has scope for are silently dropped on decode — no error, no leak.**

### RBAC scope enforcement (CAL-04 carry-forward — non-negotiable)

- The `FilterCombobox` dropdown for "Speler" calls `trpc.calendar.filterOptions.list({ kind: 'player', query: '...' })`. The server enforces scope: a trainer typing "Van" sees only players in the trainer's academy whose name matches. A speler typing "Van" sees only themselves (if name matches) — never another speler. A sparring partner sees the empty list for "Speler" filter (filter still rendered for layout consistency, but no options surface).
- Similarly for trainer / sparring partner / academie filters.
- **The filter UI never branches by role.** Always renders all 4 combos; the server returns empty option lists for filters the caller cannot use. This is critical for D-36 carry-forward: a sparring partner cannot infer "the trainer filter exists for some roles" because the UI is identical across roles — they just see an empty options list when they open it.

## Conflict Detection UI Contract (CAL-07)

Server-side overlap check is authoritative. Three UI surfaces consume the result:

### Surface 1 — Inline `<ConflictWarning>` inside `EventCreateSheet` / `EventEditSheet`

Triggered on form submit. If server returns a conflict, the submit is rejected and the response payload is rendered above the submit button:

- shadcn `<Alert variant="default">` with `AlertTriangle` icon (NOT `destructive` — conflicts are warnings, not errors; user CAN override by confirming).
- Body: localized text "Conflicteert met **{event_title}** op {start_time}–{end_time}. Toch opslaan?"
- Two buttons appear: "Toch opslaan" (primary) and "Tijden aanpassen" (secondary). "Toch opslaan" re-submits with `force: true` flag — server logs the override decision in audit_log per Phase 1 patterns.
- Conflict count display: if the server returns multiple conflicts, only the first is shown with text "**+N andere conflicten**" — keeps the warning compact.

### Surface 2 — Top-page `<ConflictBanner>` after drag-drop event move

When the user drags an event to a new time, FullCalendar fires `eventDrop`. The handler:

1. Optimistic visual update (event moves).
2. Calls `trpc.calendar.event.update({ id, newStart, newEnd })`.
3. If server returns conflict + the call has no `force: true` → server returns the conflict info, the optimistic move is **reverted** (`info.revert()`), and a top-page `<ConflictBanner>` appears with the same "Conflicteert met X" copy + a single "Ongedaan" or "Toch verplaatsen" choice.

### Surface 3 — Hint icon on the event chip (passive)

Independently of submit-time check, the calendar.list query returns events with a `conflicting: boolean` flag (server computes for the visible range). The event chip displays a tiny `AlertTriangle` icon (10px) when true. This is a hint, not blocking — it tells the TD "hey, this overlaps with something" without requiring action.

### Override audit

When user clicks "Toch opslaan" / "Toch verplaatsen" on a conflict:
- Server logs the override in `audit_log` with `action='calendar_event_conflict_override'`, the conflicting event ids, and the resolution decision. (Schema lives in Phase 1's `audit_log` table; Phase 3 just wires it.)
- This is referenced in CAL-07 acceptance criteria: TD can audit who overrode conflicts and why.

## Mobile Strategy (CAL-08)

CAL-08 requires: "Op een scherm smaller dan 480px toont de kalender één dag per kolom met swipe-navigatie."

### Decision tree

| Viewport width | View shown | Navigation |
|----------------|-----------|------------|
| ≥ 768px (`md:`) | Whatever the user selected (week default, day/month/year all available) | View switcher in toolbar |
| 640–767px (`sm:`) | Week view limited to **3 visible days** (FullCalendar `duration: { days: 3 }` override). User can still switch to month/year via view switcher. | Toolbar view switcher |
| < 640px (`sm:` minus) | **Forced single-day view (`timeGridDay`)**. View switcher hides Week + Year buttons (Month stays — month view is dense but readable on mobile). | Swipe left/right on the calendar body → previous/next day. Implemented via touch-event listeners on the FullCalendar container (NO third-party swipe library — vanilla `pointerdown`/`pointermove`/`pointerup` handler that calls `calendarRef.current.getApi().next()` or `.prev()`). Threshold: 60px horizontal drag, 200ms max duration to count as swipe (not a slow drag). |

> **Why 640px (Tailwind `sm:`) instead of CAL-08's stated 480px threshold?** The 480px boundary is the strict requirement. We use 640px as the *upgrade-to-3-day* boundary and 640px-minus as the *single-day-with-swipe* boundary, which means CAL-08's 480px constraint is automatically met (anything < 640 includes anything < 480). The relaxed boundary at 640px buys us correctness on common phone landscape widths (iPhone 14 landscape = 852pt, narrow Android = 480 width). The planner can tighten to 480px if testing shows the 480–640 range performs better as 3-day view — both are acceptable interpretations of CAL-08.

### Touch interaction on chips

- Min height 44px (declared in `## Spacing Scale` exceptions).
- Tap on chip → `EventDetailSheet` opens.
- Long-press (500ms) → reserved for future drag-to-move on mobile; **v1 disables long-press-drag** (FullCalendar `editable: !isMobile`) to avoid accidental moves. Drag-to-edit is desktop-only in Phase 3.

### Toolbar collapse

- View switcher on `< 640px`: dropdown (`Select`) instead of `ToggleGroup` to save horizontal space.
- Date navigator stays as prev / Today / next icon row.
- "Nieuwe afspraak" CTA: floats as a fixed-position `Button` bottom-right (`fixed bottom-4 right-4 md:static md:bottom-auto md:right-auto`) on mobile — keeps it reachable without scrolling but doesn't crowd the toolbar.

## RBAC-Sensitive UI Behavior

Server-side RLS (Phase 1) + tRPC `requireRole` middleware decide what events render. The UI mirrors server decisions and never branches on role client-side beyond the safe affordance rules below.

| Caller role | Events visible | Create CTA visible | Click-to-create grid | Edit affordance | Delete affordance |
|-------------|-----------------|--------------------|-----------------------|-----------------|-------------------|
| TD | all | yes | yes | yes | yes |
| academy_manager | all events of own academy's players + trainers | yes | yes | for own-academy events | for own-academy events |
| trainer | own + own-academy players + sessions they own | yes (training, meeting types only — server enforces) | yes | for own events | for own events |
| player | only own events | yes (training only — own; meeting type per AGE-02) | yes (training, meeting) | for own events | for own events; medical/tournament/eval/stage = no edit (server gate) |
| parent of player | only own child's events | no | no | no | no |
| sparring partner | only sessions they participate in | no | no | no | no |

### Visual rule for read-only calendar (sparring partner, parent)

The calendar grid still renders fully — events visible, all interactions navigatable. The differences:
1. No "Nieuwe afspraak" CTA in toolbar.
2. `selectable: false` on FullCalendar — clicks on empty grid cells do nothing.
3. Event chips clickable → opens `EventDetailSheet` in read mode. Detail sheet shows no "Bewerken" or "Verwijderen" buttons.
4. Drag-drop and resize disabled (`editable: false`).
5. Filter bar fully rendered. Combo dropdowns return empty option lists for filters the role can't use (e.g. sparring partner sees empty results for "Speler" combo) — the UI is identical, the server result is empty.

This guarantees a sparring partner cannot infer "there exist other roles with broader access" — the calendar visually behaves identically across roles, with affordances shown only when the server permits the action.

## Loading & Error States

### Initial-paint loading

- `<CalendarSkeleton>` (declared in component inventory) renders during the Suspense boundary while the page server-fetches the visible-range events.
- Skeleton dimensions match the final calendar (same number of grid rows + columns) → zero CLS.
- Maximum visible loading time before showing skeleton: 200ms (Suspense `loading.tsx` timing — implementation detail for planner).

### Range navigation loading

- When user clicks prev/next/today, FullCalendar's internal navigation is instantaneous (events already on the client) for the current visible window plus one window before and after (pre-fetch). When navigating beyond the prefetch window, a thin progress bar (1px tall) appears at the top of the calendar grid in `--primary` while data fetches.
- No skeleton flash for navigation — events animate in.

### Network / data errors

- `trpc.calendar.list` failure: page-level `<Alert variant="destructive">` slot at the top of the calendar with `errors.generic` + "Probeer opnieuw" button. Sentry captured server-side (Phase 1 carry-forward).
- Event create/edit network failure: shadcn `Sonner` toast with `calendar.event.toast.error`. The form retains its values.
- 403 from API (should be rare — RLS returns 0 rows = 404): toast with `errors.forbidden` (Phase 1 catalog).
- 404 from `calendar.event.get` (deep link to event out of scope): toast with `calendar.event.toast.notFound` + URL strips `?event=` automatically. Visually indistinguishable from "event was deleted" — never reveals scope (D-36 carry-forward).
- Optimistic drag-drop / resize failure: optimistic state reverts, sonner toast with `calendar.event.toast.error`, event snaps back to original position.

### Background polling / refresh

- No polling in Phase 3. Calendar refreshes only on user navigation (range change), explicit user "Refresh" action (deferred — out of Phase 3 scope), or after a successful create/edit/delete mutation (which invalidates the React Query cache).
- Realtime updates via Supabase Realtime → introduced in **Phase 6 (Messaging)** for inbox, can extend to calendar in v2 (`NOTIFICATION-PREFS` in deferred reqs). Phase 3 explicitly skips realtime to keep complexity tied to one phase.

## Accessibility Contract

- All interactive components reachable by keyboard. Tab order follows DOM order (toolbar → filter bar → calendar → sheet if open). No `tabindex` > 0.
- Color never the only signifier. Event type also conveyed via lucide icon in chip. Status overlays (past, recurring, conflict) also use icon glyphs.
- Contrast: tinted event chip backgrounds + deep fg pass WCAG AA at 14px / 500 weight. Each `--cal-event-{type}-{bg,fg}` pair has been chosen so `oklch(bg) ↔ oklch(fg)` lightness delta ≥ 0.55 — well above the 4.5:1 AA threshold.
- Focus: FullCalendar events receive focus ring via `--ring` token (overridden via FC's `--fc-event-selected-overlay-color`). Custom Sheets / Combos use shadcn defaults.
- Screen reader announcements:
  - `<CalendarView>` is `<div role="application" aria-label="…">` per FullCalendar convention.
  - Each event chip's `aria-label` concatenates type + title + start–end time (set via `eventDidMount`).
  - Toolbar icon-only buttons (prev, next, today) use their respective i18n key as the `aria-label` source — `calendar.actions.prev`, `calendar.actions.next`, `calendar.actions.today` — so the visible label and screen-reader label share a single translation row.
  - View change announces "Nu week 21 van 2026" via `<div role="status" aria-live="polite">` hidden visually.
  - Date change on prev/next announces "Week 22 van 2026" similarly.
  - Conflict warning uses `aria-live="assertive"` (interrupts speech — conflicts need attention).
- Sheet dialogs trap focus and restore on close (Radix default — shadcn Sheet uses Radix Dialog under the hood).
- 44×44 minimum hit target rule (Phase 2 D-…) applies to: event chips on mobile, all icon-only buttons in `CalendarToolbar`, "Nieuwe afspraak" FAB on mobile.
- Reduced motion: `@media (prefers-reduced-motion: reduce)` disables the slide-in animation on Sheets, fades only. Drag-drop optimistic motion stays (functional, not decorative).
- Keyboard shortcuts (Phase 3 v1 — minimal set):
  - `?` opens a tooltip listing the available shortcuts (deferred to Phase 8 polish; UI scaffold present in Phase 3).
  - `←` / `→` on focus inside calendar = prev / next range.
  - `t` = today.
  - `w` / `d` / `m` / `y` = switch view.
  - `n` = "Nieuwe afspraak" (only when role permits create).
  - `Esc` closes any open Sheet.
