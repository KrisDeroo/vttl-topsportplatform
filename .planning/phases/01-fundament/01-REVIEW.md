# Phase 1 (Fundament) — Adversarial Code Review

**Reviewed:** 2026-05-01
**Depth:** standard
**Status:** issues_found

## Summary

113 files reviewed across `src/`, `drizzle/`, `tests/integration/`, `tests/rls/`, and `.github/workflows/`. The architecture is solid (RLS-as-backstop, two-role split, append-only audit, encrypted medical, three-locale email contract) but several **BLOCKER**-class defects ship with the phase:

- A migration that **cannot apply** (`CURRENT_DATE` in a STORED generated column).
- An **authorization bypass** in `consent.give` that lets any authenticated user record consent on behalf of any victim.
- The platform-wide consent gate (`requireCurrentConsent`) **deadlocks first-time users**: they cannot give consent because they have no consent.
- A **duplicate auth file** (`auth 2.ts`) shipped to `src/` exporting a competing, stub-email Better Auth instance.
- The RLS GUC for `app.medical_key` is **set inside the tRPC transaction**, so the per-connection contract documented in `helpers/encryption.ts` is broken for any non-tRPC code path (workers, seed scripts, GDPR erasure functions).
- An unfresh-session check on `requireFreshSession` skips its anchor — `ctx.scope?.fresh` evaluates `undefined` ↔ `false`, but composition order means anonymous calls reach this gate via `sensitiveProcedure → requireFreshSession` BEFORE `requireAuth` if `sensitiveProcedure` is used as a base elsewhere; the comment in `freshSession.ts` calls this "defence in depth" but the practical outcome is "anonymous calls return `re_auth_required` instead of `UNAUTHORIZED`" — leak channel.

The medical isolation contract (RLS + write-time triggers + INSERT-only role grants) verifies cleanly. The Belgian-Art.8 UNIQUE constraint on `parent_child_links.child_user_id` is correctly placed.

## Critical (BLOCKER)

| ID    | File:line                                                | Category | Finding |
|-------|----------------------------------------------------------|----------|---------|
| CR-01 | `drizzle/0003_users_is_minor.sql:30-38`                  | bug      | `GENERATED ALWAYS AS (CASE WHEN ... CURRENT_DATE - date_of_birth) ...) STORED` is **rejected by Postgres** — generated-column expressions must be `IMMUTABLE`. `CURRENT_DATE` is `STABLE`. The migration will fail at apply time with `ERROR: generation expression is not immutable`. The whole minor-consent gate (Plan 12 / `canActivate`) is broken at the schema layer. **Fix:** Drop the generated column and compute `is_minor` per-query with a regular function or materialised view, OR encode the threshold as a `date_of_birth` predicate evaluated at RLS/policy time. Even a `BEFORE INSERT/UPDATE` trigger that writes to a regular boolean column is correct; a STORED generated column is not. |
| CR-02 | `src/server/trpc/routers/consent.ts:97-141`              | security | `consent.give` accepts `forUserId: z.string().uuid().optional()` and unconditionally writes the row with that `userId` and `consentingPartyUserId = callerId`. RLS policy `consent_inserts` (Migration 0002 line 305-310) lets any row through whose `consenting_party_user_id = current_user_id()`. Net effect: **any authenticated user can record an "operational" consent on behalf of any other user**, including manufacturing a parent-on-behalf-of-minor consent without an actual `parent_child_links` row. This silently legitimises onboarding fraud and corrupts the GDPR Art. 8 evidentiary trail. **Fix:** when `forUserId !== callerId`, verify (a) caller has `consent.give_for_minor` permission, (b) a `parent_child_links` row exists with `parentUserId = callerId AND childUserId = forUserId`, and (c) the target's `is_minor IS TRUE`. Reject otherwise. Also tighten the RLS policy: `WITH CHECK ((user_id = current_user_id()) OR (current_user_role() = 'technical_director') OR (consenting_party_user_id = current_user_id() AND user_id IN (SELECT child_user_id FROM parent_child_links WHERE parent_user_id = current_user_id())))`. |
| CR-03 | `src/server/trpc/routers/consent.ts:97` and `src/server/trpc/middleware/freshSession.ts:82-85` | bug | `consent.give` is composed on `protectedProcedure`, which chains `requireCurrentConsent`. A first-time user (or a user after a major version bump) has no row at `CURRENT_POLICY.operational.version`, so `requireCurrentConsent` throws `re_consent_required` BEFORE `consent.give` runs. Result: the only endpoint that creates a consent row is itself gated on already-having one — **the consent banner can never proceed**. The router-file comment claims the middleware "tolerates this", but the implementation does not (only `null`-scope short-circuits to `next()`). **Fix:** Move `consent.give` to a dedicated procedure preset that runs `requireAuth + withRlsContext` only (no `requireCurrentConsent`). Equivalent in `freshSession.ts`: `export const consentGiveProcedure = publicProcedure.use(requireAuth).use(withRlsContext);`. |
| CR-04 | `src/lib/consent.ts:170-209` and `src/server/trpc/routers/consent.ts:103` | security | `recordConsent({ textShown })` SHA-256-hashes whatever bytes the client sends and stores them as the legal snapshot. The router's only gate is `z.string().min(50)`. An attacker (or buggy frontend) can submit arbitrary text and have it stored as a "legally binding consent" — the SHA-256 is over the attacker's text, so the tamper-evidence drill in `tests/integration/consent.test.ts:78-115` passes for fabricated content. **Fix:** Server-side, re-read the canonical text via `getConsentText(category, version, locale)` and (a) reject if `args.textShown !== canonical`, OR (b) ignore `args.textShown` entirely and snapshot the canonical bytes the server holds. Option (b) is simpler and safer; option (a) preserves the on-screen-bytes audit but adds an equality check. |
| CR-05 | `src/server/auth/auth 2.ts` (entire file)                | bug/security | Duplicate Better Auth instance shipped alongside `auth.ts`. Same `export const auth = betterAuth(...)` symbol, but with `sendResetPasswordStub` / `sendVerificationEmailStub` (console.warn only — no email sent in production). Whether this gets imported depends on bundler tie-breaking and module-resolution order; the file's existence is a non-deterministic landmine. **Fix:** Delete `src/server/auth/auth 2.ts` and verify only `src/server/auth/auth.ts` is referenced from `src/app/api/auth/[...all]/route.ts`, `src/server/trpc/server-context.ts`, etc. (current imports look correct, but the duplicate file should not survive review). |
| CR-06 | `src/server/trpc/middleware/rls.ts:81-83`                | security | `app.medical_key` is `set_config(..., true)` — bound to the current transaction. The encryption helper docstring (`src/server/db/helpers/encryption.ts:23-26`) explicitly says "every connection that touches `medical_*` tables MUST have `app.medical_key` set" and references "Plan 06's pool initializer". No such initializer exists in `src/server/db/client.ts`. Consequence: any code path that writes/reads medical envelopes **outside** an RLS-bound tRPC transaction (BullMQ workers, seed scripts in `tests/helpers/seed.ts:91-93`, future GDPR erasure cron, the Phase-7 SECURITY DEFINER read function) will fail with `unrecognized configuration parameter "app.medical_key"`. The seed already works around this by setting the GUC manually with `is_local=false`; production code paths cannot rely on transaction-scoped GUCs for the encryption key. **Fix:** Add `onconnect` to the `postgres()` constructor in `src/server/db/client.ts` that issues `SET app.medical_key = '<env>'` once per pooled backend. Keep the per-transaction set in `withRlsContext` for layered defence, but the pool-init binding is the contract the encryption helpers rely on. |
| CR-07 | `src/app/[locale]/(app)/admin/users/page.tsx:56-59`      | security | `db.query.users.findMany({...})` runs as the schema-owner connection (via `@/server/db/client`), which bypasses RLS. The page redirects non-TD users via `if (role !== 'technical_director')`, but the role check reads from `session.user.role` — a Better Auth field that is *not* tied to the DB role on the connection. Combined with CR-06's GUC behaviour, a TD impersonator (e.g. via Better Auth role-claim manipulation in v1.1, or a future bug that lets a non-TD reach this Server Component) gets the unredacted user list including `dateOfBirth` and `isMinor`. **Fix:** The TD admin page should call the tRPC `admin.user.list` procedure server-side via `appRouter.createCaller(ctx)` so the same RLS + permission chain that protects the client also protects the server-rendered initial data. Alternatively, accept the bypass but document it explicitly (it conflicts with the comment "mutations from the Client Component go through tRPC where RLS is honoured per-request"). |

| WR-01 | `src/server/trpc/middleware/requireConsent.ts:60`        | bug      | `const rows = Array.isArray(stale) ? stale : [];` defends against `db.execute` returning a non-array, but the failure mode is silent: if `Array.isArray(stale)` returns `false` for any reason (postgres-js result wrapper change, transaction handle quirk), the consent gate is skipped entirely (`rows.length === 0 → next()`). **Fix:** treat any non-array shape as an explicit failure — `if (!Array.isArray(stale)) throw new TRPCError({ code: 'INTERNAL_SERVER_ERROR', message: 'consent_check_unexpected_shape' });`. Fail closed, not open. |
| WR-02 | `src/server/trpc/middleware/freshSession.ts:43-51`       | bug      | `if (!ctx.scope?.fresh)` returns FORBIDDEN `re_auth_required`. When `ctx.scope === null` (anonymous), `ctx.scope?.fresh === undefined` and the same error is thrown — a public caller is told to "re-authenticate" instead of "authenticate". Information-disclosure-grade leak channel: `requireFreshSession` reveals that the procedure exists. **Fix:** `if (!ctx.scope) throw UNAUTHORIZED; if (!ctx.scope.fresh) throw FORBIDDEN re_auth_required;`. Same correction pattern as the existing `requireRole` (which also collapses null-scope into `role_not_allowed` — flagged separately if you fix one, fix both). |
| WR-03 | `src/server/trpc/middleware/freshSession.ts:58-67`       | bug      | `requireRole`: `if (!ctx.scope || !roles.includes(ctx.scope.role))` collapses "anonymous" and "wrong role" into the same `FORBIDDEN role_not_allowed` error. Anonymous callers should receive `UNAUTHORIZED` so the UI can route them to login, not to an unhelpful "your role is not allowed" page. **Fix:** check `ctx.scope` for null first and throw `UNAUTHORIZED`. |
| WR-04 | `src/server/trpc/server-context.ts:88-89`                | security | `const role = (u.role ?? 'player') as Role;` defaults an unknown user-row role to `'player'`. If Better Auth ever returns a row whose `role` field is missing (schema drift, additional-fields plugin misconfig, partial migration), the user gets `'player'` permissions silently — acceptable for non-privileged endpoints but inverted-defence-in-depth for privileged paths. **Fix:** `const role = u.role && (ROLES as readonly string[]).includes(u.role) ? u.role : null;` — and reject the request when role resolution fails (or treat as anonymous). |
| WR-05 | `src/server/trpc/server-context.ts:78-86`                | bug      | `const sessionRow = (session.session ?? {}) as { freshUntil?: Date \| string \| null };` then `freshUntilMs = freshUntilRaw instanceof Date ? freshUntilRaw.getTime() : typeof freshUntilRaw === 'string' ? Date.parse(freshUntilRaw) : 0;`. On a freshly issued login, Better Auth sets `freshUntil` to `now + freshAge`. If the session-cookie cache returns the field as a number (epoch-ms), the code falls into the `else 0` branch and `fresh = false` for the entire window. This is a contract bug between Better Auth v1.6 (which serialises `Date` objects in cache differently per backend) and the consumer. **Fix:** add `typeof freshUntilRaw === 'number'` arm; `if (typeof freshUntilRaw === 'number') freshUntilMs = freshUntilRaw;`. Also add explicit logging for the unhandled-shape case so a regression is observable. |
| WR-06 | `src/lib/log-redact-paths.ts:50`                         | security | `'*.medical_*'` — pino's redact engine (fast-redact) does NOT support partial-segment globs in the trailing path component. The pattern matches a property literally named `medical_*` (asterisk character), not all properties starting with `medical_`. The `tests/unit/log-redact.test.ts` only checks the array contains the string, not that pino redacts. Effective consequence: keys like `medical_diagnosis`, `medical_history`, etc. flow through unredacted. **Fix:** enumerate explicit fields (`*.medicalDiagnosis`, `*.medicalHistory`, …) OR use pino's `serializers` with a function that wipes any key starting with `medical_`. Mirror the same fix in `src/lib/sentry.ts:93-97` (which DOES use a runtime check `k.startsWith('medical_')` — only Sentry is correct; pino is not). |
| WR-07 | `src/server/trpc/middleware/audit.ts:128-135`            | bug      | `auditMiddleware`: on procedure rejection, `await writeAudit(...)` runs OUTSIDE the original transaction (the rejection has already aborted the surrounding `tx`). `writeAudit` falls back to `rawDb` and writes the error row, but the actor's `app.user_id` GUC is no longer set on `rawDb` — the audit row's `actor_user_id` may be null (depending on whether the caller's tx-scoped GUC propagated). Result: failed-RBAC audit rows lose attribution. **Fix:** persist actor identity from the surrounding context (`ctx.scope?.userId`) into `writeAudit`'s argument before the rejection clears the GUC; this already happens — the bug is that the row inserts via a DIFFERENT connection (rawDb) that may have no GUC set. Use a fresh transaction with explicit `set_config` for the audit row, or accept the loss of `actor_user_id` for error rows and document it. |
| WR-08 | `src/i18n/request.ts:60-62`                              | bug/UX   | `const final = hasLocale(routing.locales, locale) && locale !== routing.defaultLocale ? locale : resolved;` — when the URL segment IS the default locale (`nl`), the cookie/userPref overrides it. A user explicitly visiting `/foo` (default `nl`) with `cookie=en` sees English on a Dutch URL. The docstring claims "Prefer the URL-segment locale if it diverges" but the implementation excludes the default-locale URL from URL-priority. **Fix:** distinguish "URL implies a non-default locale" from "URL implies the default locale" — both are explicit user intent; only "URL is locale-less" should defer to cookie. Adjust the predicate or revisit the docstring; current code does NOT match documented behaviour. |
| WR-09 | `src/server/trpc/routers/consent.ts:249-261`             | security | `_enqueueVersionBump` is on `protectedProcedure` (any authenticated user), but it enqueues a BullMQ job for an arbitrary `userId` to receive a "consent updated" email. Net effect: any authenticated user can trigger spam emails to any other user (via `consentNotifyQueue`). The docstring says "Phase 1 ships the surface; the call site is out of scope" — but the surface is *exposed* on `appRouter`. **Fix:** Move to `tdProcedure` (only the technical director should bump versions and trigger fan-out), OR remove from `_app.ts` until Plan 15 wires the admin UI. The leading underscore in the name does not enforce anything — tRPC happily exposes it. |
| WR-10 | `drizzle/0002_rls_functions_and_policies.sql:240-243`    | security | `verifications_consume` policy: `FOR ALL USING (true) WITH CHECK (true)`. This grants every connection (including app_user) full SELECT/INSERT/UPDATE/DELETE on `verifications`. Better Auth's tokens are unguessable, so SELECT-by-token is fine, but UPDATE/DELETE-without-scoping lets any caller invalidate ANY pending verification (e.g., delete a competitor's verify-email token before they click it). **Fix:** restrict UPDATE/DELETE to rows where `identifier = current_user_email()` or rely on row-level scoping; or accept and document the trade-off (Better Auth normally rotates tokens on consume, so the window is narrow but real). |
| WR-11 | `src/server/db/schema/consent.ts:52`                     | bug      | `consentingPartyUserId` is nullable. The `consent_inserts` RLS policy WITH CHECK (`user_id = current_user_id() OR consenting_party_user_id = current_user_id() OR td`) lets a TD insert a row with `consenting_party_user_id = NULL` — orphaned consent with no attributable agent. The Belgian Art. 8 audit trail requires this column to identify "who clicked agree". **Fix:** make the column `NOT NULL` in a new migration; back-fill existing rows by setting `consenting_party_user_id = user_id` for adult self-consents. |
