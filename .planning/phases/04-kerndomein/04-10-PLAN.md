<objective>
Close CR-01 (Phase 4 VERIFICATION.md): denied-outcome audit rows must survive
the rollback of the failing transaction so the forensic-visibility property the
T-04-19 / T-04-23 / D-83 inline comments already claim is actually delivered.

Today, every `writeAudit(ctx, { outcome: 'denied' })` call in training,
tournament, and calendar wall-rejection / past-immutable paths runs through
`ctx.db` — the open `withRlsContext` transaction handle. The next line throws a
TRPCError; Drizzle rolls the whole tx back; the audit row vanishes. The GDPR
Article 30 feed is silently missing every wall-expired attempt and every
edit-past-occurrence attempt.

The fix follows the pattern `auditMiddleware` (audit.ts:136-158) already uses
on its rejection path: strip `ctx.db` and let `writeAudit` fall back to the raw
pool, which is not bound to the failing tx. The audit_log RLS INSERT policy is
`WITH CHECK (true)` (drizzle/0002 line 343), so the rawDb insert succeeds
without per-request GUCs.

Purpose: deliver D-67 / D-72 / T-04-19 / T-04-23 / GDPR-04 forensic visibility
on FORBIDDEN paths. Every denied write attempt MUST be recoverable from
audit_log even after the failing tx rolls back.

Output: writeAuditOutsideTx helper in audit.ts + 4 router call-site refactors +
one integration test that probes all four paths against the live DB.

```typescript
/**
 * Variant of `writeAudit` that deliberately strips `ctx.db` so the insert
 * runs on the raw pool, not on the surrounding withRlsContext transaction.
 *
 * Why: explicit `writeAudit(ctx, { outcome: 'denied' })` calls in router
 * handlers (training.markAttendanceAndScore wall-rejection,
 * tournament.enterResult wall-rejection, calendar.editRecurring
 * past-immutable rejection) are followed by `throw new TRPCError(...)`,
 * which rolls the open tx back — including the audit row. The
 * forensic-visibility property documented in T-04-19 / T-04-23 / D-83
 * threat-mitigation comments is broken unless the audit insert commits
 * outside the failing tx.
 *
 * `auditMiddleware` (below) already applies this pattern on its rejection
 * path. This helper formalises the same shim so explicit denied-audit
 * call sites can compose it without duplicating the strip-context
 * boilerplate.
 *
 * Caveat: actor attribution comes from `ctx.scope.userId` (passed through
 * in the row payload), NOT from the `app.user_id` Postgres GUC — the
 * rawDb pool connection does not have the GUC set. This matches the
 * auditMiddleware error path behaviour. The audit_log INSERT policy is
 * `WITH CHECK (true)` (drizzle/0002 line 343) so the insert succeeds.
 *
 * Reference: .planning/phases/04-kerndomein/04-REVIEW.md §CR-01
 *            .planning/phases/04-kerndomein/04-VERIFICATION.md §gaps[0]
 */
export async function writeAuditOutsideTx(
  ctx: AuditContext,
  entry: AuditEntry,
): Promise<void> {
  const strippedCtx: AuditContext = {
    scope: ctx.scope ? { userId: ctx.scope.userId } : null,
    ipAddress: ctx.ipAddress,
    userAgent: ctx.userAgent,
    requestId: ctx.requestId,
    // db deliberately omitted — writeAudit falls back to rawDb.
  };
  await writeAudit(strippedCtx, entry);
}
```

`auditMiddleware` definition. The helper reuses the existing `AuditContext` /
`AuditEntry` interfaces and the existing `writeAudit` function — no new
imports needed.
